## How terminal mouse works (the mental model)

A TUI app doesn't see hardware mouse events. It works like this:

1. The **app** requests mouse reporting by writing enable sequences to its stdout, e.g. `ESC[?1000h ESC[?1002h ESC[?1006h`.
2. The **terminal emulator** (the thing that owns the screen grid) intercepts real pointer input and converts it into escape sequences written to the PTY **master**.
3. The **app** reads those bytes from its stdin and its parser (e.g. crossterm) turns them back into `MouseEvent`s.

So your tool is the emulator. To inject mouse, it must encode the event into the exact sequence the app requested, and write it to the PTY master.

## The escape sequences you must emit

### Enable / disable tracking modes (`h`=on, `l`=off)

| Mode                    | Meaning                    | Sequence     |
| ----------------------- | -------------------------- | ------------ |
| Normal tracking         | press/release only         | `ESC[?1000h` |
| Button-event tracking   | + drags                    | `ESC[?1002h` |
| Any-event tracking      | + all motion               | `ESC[?1003h` |
| SGR extended encoding   | large coords, rich buttons | `ESC[?1006h` |
| urxvt extended encoding | alt large-coord format     | `ESC[?1015h` |

### Event encodings

**X10 (default when 1006/1015 are off)** — coords limited to ≤223:

```
ESC[M {b+32} {x+32} {y+32}     // press/drag
ESC[M {3+32} {x+32} {y+32}     // release (button code 3)
```

(b, x, y are bytes; add 32 to each; x/y are 1-based.)

**SGR (1006) — prefer this:**

```
ESC[<b;x;yM    // press / drag / motion / wheel
ESC[<b;x;y m   // release (lowercase 'm')
```

x,y are 1-based column,row.

### Button / modifier code `b` (used by both SGR and urxvt)

| Meaning                | `b`   |
| ---------------------- | ----- |
| left press             | `0`   |
| middle press           | `1`   |
| right press            | `2`   |
| **drag / motion flag** | `+32` |
| scroll up              | `64`  |
| scroll down            | `65`  |
| shift                  | `+4`  |
| meta/alt               | `+8`  |
| ctrl                   | `+16` |

Examples:

- left click at (10,5): `ESC[<0;10;5M` + `ESC[<0;10;5m`
- right click at (3,8): `ESC[<2;3;8M` + `ESC[<2;3;8m`
- wheel down at (40,20): `ESC[<65;40;20M`
- left-drag to (12,6): `ESC[<32;12;6M`

## The messages the host must track (from app output)

To encode correctly you need state extracted from the app's stdout:

1. **Tracking mode** — parse `ESC[?1000/1002/1003 h|l`. Only deliver mouse when a tracking mode is active; otherwise the app's parser will treat your bytes as garbage input (this is a real hazard).
2. **Encoding mode** — parse `ESC[?1006h`/`ESC[?1015h`. Pick the encoding accordingly.
3. **Screen dimensions** — so `(x,y)` clamp to the grid and map to real cells.

So your `terminal_read` screen already gives the grid; add a `mouse_state` field to it (tracking mode + encoding + dims) so the agent knows whether a click will actually land.

## Gotchas for your implementation

- **Send the whole sequence in one write.** Parsers like crossterm are stateful; a partial write can wedge them or corrupt the next event.
- **Release differs per encoding** — SGR lowercase `m`, X10 button code `3`. Getting this wrong means click-hold-release never registers as a click.
- **Coords are 1-based** and go to the emulator's grid, matching what `screen`/`screen_cursor` show.
- **Wheel is discrete** (no wheel-drag). ScrollUp/Down only; no horizontal by default.
- **Prefer SGR (1006).** It's what modern terminals and crossterm default to, handles big terminals, and distinguishes modifiers cleanly. If the app never enabled 1006, fall back to X10 and cap coords at 223.
- **Many TUI apps don't enable mouse by default** (vim, htop, less). Either let the agent send `ESC[?1000h` itself, or expose an `enable_mouse()` helper. Mouse capture is commonly gated behind a flag in the app.
